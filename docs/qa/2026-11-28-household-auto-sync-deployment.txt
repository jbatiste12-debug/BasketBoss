Lock/lifecycle compatibility
----------------------------
Live receipt service:confirmed identity -> household FOR SHARE -> existing
bb-receipt:<scope-kind>:<scope-id> advisory lock -> inventory scope FOR UPDATE.
Live deletion RPC:households ORDER BY id FOR UPDATE -> each receipt advisory lock
-> personal receipt advisory lock -> auth.users FOR UPDATE -> existing cleanup.
Live unlink retains household FOR UPDATE. These existing functions are unchanged.

New sync:household FOR SHARE -> confirmed auth identity FOR KEY SHARE -> sync
metadata advisory lock/clock row -> existing household receipt advisory lock ->
existing inventory row -> independent dinner/setting leaves. The patched legacy
CAS takes the same sync advisory lock after its existing membership/share check.
Receipt never acquires sync metadata, and supported deletion obtains the household
lock before the auth lock. No opposing metadata/receipt lock dependency is added.
Local real-PostgreSQL verification covers receipt interleaving, actual deletion
draining in-flight work, unlink, atomic meal/servings, pruning and duplicate
acknowledgments with unchanged row values/revisions/timestamps.
